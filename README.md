# Jukebox: phased build kit

This kit builds the game by running about 30 small Claude Code sessions in a row. Each session starts fresh (so it never nears your 130k context limit), does one job, marks itself done, and the driver starts the next. Progress is saved in files, so you can stop and resume any time.

## Run it
1. Install Claude Code and sign in. Install Node 18+, git, and the GitHub CLI (`gh auth login`).
2. Unzip this folder, open a terminal in it, and copy the env file: `cp .env.example .env`.
3. (Optional) create your Supabase project now and fill in `.env`. If you skip this, step 01 stops and tells you exactly what to click.
4. Start: `node run_phases.mjs`
5. If it stops with "this step needs you", do what it says, then run the same command again. It resumes where it stopped.

Other commands: `--status` (progress), `--dry-run`, `--only 04`, `--from 08a`, `--reset 09a` (redo a phase), `--render <phase>` (write that phase's prompt so you can paste it into an interactive `claude` session yourself).

Options (environment variables): `PARALLEL=3` (song checkers at once), `SONG_MULTIPLIER=2` (about 4,100 songs instead of 2,050), `MAX_ATTEMPTS=3`, `MAX_TURNS=200`, `MODEL_A` / `MODEL_B` (use different models for the two year verifiers), `CLAUDE_FLAGS`.

## What happens, in order
Preflight, repo and Supabase setup, game logic with tests, song curation (8 decade sessions), two blind year verifications in chunks of 40, reconciliation and research of disagreements, Apple preview matching (runs for hours on your machine; resumable), then Supabase layer, lobby, Closest Year, Timeline, blocklist, a bot simulation, and deploy to GitHub Pages. At the end, read `.build/PLAYTEST.md`.

## Keeping the surprise
Song details are never printed by the tools or the agents. The files in `data/work/` and `app/public/songs.json` contain the answers, so don't open them. Don't read `.build/logs/` either.

## Heads up
- The agents run unattended with permission to edit files and run shell commands (`--permission-mode acceptEdits`, Bash allowed). Run it only inside this folder. Change `CLAUDE_FLAGS` for stricter settings (the run will then stop at prompts).
- The blind verifiers are blocked from reading the curator's answers by tool rules; this is best effort.
- Cost: many sessions with a lot of web research. Watch your plan limits; the driver prints per-session cost when available.
- The plan is in `PLAN.md` (split into `plan/`). Edit those files to change the game before the relevant phase runs.

# Jukebox: how to run things

Repo layout: `app/` (web app, Vite + TypeScript), `supabase/migrations/` (SQL), `tools/` (scripts), `phases/` (phase prompts), `data/work/` (song pipeline, git-ignored), `.build/` (build notes and state).

| Task | Command |
| --- | --- |
| Install app deps | `cd app && npm install` |
| Install tool deps (smoke tests) | `npm install` (repo root) |
| Copy Supabase URL + publishable key into `app/.env` | `node tools/sync-app-env.mjs` |
| Dev server (phones on the same Wi-Fi can use the printed network URL) | `cd app && npm run dev` (open `/jukebox/`) |
| App tests | `cd app && npm test` |
| Production build | `cd app && npm run build` (output in `app/dist`) |
| Set the two GitHub repository variables from `.env` (once) | `node tools/set-pages-vars.mjs` |
| Realtime + database smoke test | `node tools/smoke-realtime.mjs` |
| Apple preview smoke test (about 70 s, counts only) | `node tools/smoke-itunes.mjs` |
| Bot simulation against the real project (about 3 min, counts and timings only) | `node tools/simulate.mjs` (options: `--modes timeline`, `--bots 10`, `--rounds 8`, `--target 6`, `--seconds 15`) |

Secrets live in the root `.env` (git-ignored). Only `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` go to the browser (as `VITE_*` variables in `app/.env` or GitHub repository variables `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; the key is publishable, not secret). `SUPABASE_DB_URL` is used locally only, to apply migrations.

## Song pool

Song pool: 2050 songs (1950s: 40, 1960s: 140, 1970s: 350, 1980s: 400, 1990s: 400, 2000s: 350, 2010s: 300, 2020s: 70). Built by `node tools/finalize-songs.mjs` from the verified songs and the resolved Apple preview links; only songs with a working preview are kept, non-extra songs first, then extras, up to each decade target.


## Realtime volume (free tier)

Measured by `node tools/simulate.mjs` (12 bot phones + host for the full run, 20 for `--quick`, every WebSocket frame counted, with bots refreshing every 6 to 16 s, which is far more churn than a real party). Supabase Free limits ([docs](https://supabase.com/docs/guides/realtime/limits)): 200 concurrent connections, 100 messages per second, 100 channel joins per second, 20 presence messages per second, 2 million messages per month. A database change counts once for each client listening to it.

| Measure | Result (12 phones + host) | Free limit |
| --- | --- | --- |
| Concurrent connections | 13 | 200 |
| Messages to clients per minute of play | about 3,200 to 3,500 (Closest Year 6 rounds: about 3,900 per game; Timeline: about 2,700 to 3,100) | n/a |
| Mix | database changes 4,514, presence 2,153, other 0 (two games) | n/a |
| Database changes by table | players 2,249, round_locks 1,390, rooms 517, rounds 358 | n/a |
| Peak in one second | 196 to 281 (a reveal: about a dozen player rows times 13 listeners), 14 of 119 active seconds above 100 | 100 per second |
| Channel joins (all refreshes included) | about 106 to 154 per game over 50 to 70 s (about 2 per second on average) | 100 per second |
| Monthly budget | about 650 messages per round including the refresh churn, so a 20-round game is roughly 15,000 messages and the 2 million allowance is about 130 such games a month | 2 million |

**At the 20-player limit.** `node tools/simulate.mjs --quick` (20 bots, 2 rounds in each mode, one refresh) peaked at 21 connections, so the 200-connection cap is far away. Each database change is sent to every listener, so a reveal costs about 20 player rows times 21 listeners, roughly 400 messages in one second, against the nominal 100 per second. The 12-phone numbers above scale up by about 1.7 times for bursts and about 3 times for the whole game (more rows times more listeners). The same fixes apply if the burst ever gets enforced. The 2 million monthly messages stay fine (a 20-player game is a few tens of thousands).

Reading: connections, joins and the monthly allowance have a lot of headroom. The one number above its nominal limit is the burst at each reveal. No bot was disconnected and no update was lost in 2 runs of 2 games, but if Supabase ever starts enforcing 100 per second on a free project, the cheapest fixes are (1) phones stop listening to the `players` table and read their own row through `get_my_state`, and (2) the host writes all players in one statement and the scoreboard is rebuilt from the reveal payload. Not done now, to keep the app small.

# Decisions

Each architecture decision and the reason for it. Add to this list as phases make more.

- **Frontend stack: Vite + TypeScript, no UI framework (yet).** Builds to plain static files, loads fast on phones, tiny toolchain. A framework can be added later if the screens need it; the game logic stays framework-free.
- **Hosting: GitHub Pages from a public repo named `jukebox`, base path `/jukebox/`.** Free Pages needs a public repo; Nathan accepts the song file being publicly readable. Deployed by a GitHub Actions workflow (`.github/workflows/deploy.yml`, finished in phase 13).
- **Backend: Supabase (Postgres + Realtime), no custom server.** Chosen by Nathan. Browser gets only the publishable key; Row Level Security is applied to every table (phase 08+).
- **Build-time config:** `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in `app/.env` (git-ignored) locally, and as GitHub repository variables in CI (the publishable key ships to every browser anyway, so a secret would add nothing).
- **Tests: Vitest** for pure game logic, because it shares Vite's config and needs no extra setup.
- **Tool scripts are plain Node ESM in `tools/`** with their own root `package.json` (`@supabase/supabase-js`, `pg`), so the web app's dependencies stay minimal.
- **Audio: Apple iTunes Search API previews, streamed from Apple's URLs, never downloaded or re-hosted** (see plan/07-audio.md). Smoke test: 20 of 20 previews returned audio.
- **Host-authoritative: the host browser runs the game, Postgres holds the state.** The host loads the static song file, computes rounds, scores and timelines with the pure functions in `app/src/logic/`, and writes the results through RPCs. Nothing about the rules is duplicated in SQL (one implementation, one set of tests). Every piece of state lives in the database (room, players with score and timeline, rounds, answers, play history, blocklist), so a host refresh calls `host_get_state` and rebuilds the screen; the game does not end. The alternative (rules in database or edge functions) would mean porting the matcher, scoring and tie-breaks to a second language. Cost: a modified host browser could cheat, which is accepted for a friends-only party game.
- **No sign-in, so security is by token, and all writes go through functions.** Creating a room returns a long random host token; joining returns a long random seat token. Both are kept in `localStorage`. Four tables (`rooms`, `players`, `rounds`, `round_locks`) are readable by anyone and have no write policy at all. The six others (`room_secrets`, `player_secrets`, `round_secrets`, `answers`, `play_history`, `blocklist`) have an explicit deny-all policy. The 19 `SECURITY DEFINER` functions (`search_path` empty, `EXECUTE` revoked from `PUBLIC`) check the right token themselves. RLS is on for all 10 tables (`node tools/apply-migrations.mjs --verify` prints the counts).
- **Phones never get the current song before reveal.** The song id sits in private `round_secrets` (even an id such as `1980s-014` leaks the decade). The public `rounds.reveal` column is null until the host reveals; answers are private, and the public `round_locks` only says who has locked in. Only the four public tables are in the Realtime publication, so no answer, token or song id travels over Realtime. The host path (`host_get_state`) is the only way to read the current song id, and the pool answer key is the static song file the host already holds.
- **Joining:** by room code and name. A browser that remembers its seat resumes it by token, whatever the connected flag says. Otherwise a name held by a *live* seat is rejected ("That name is already taken, please choose another.") and a name whose player has dropped is taken over, which rotates the seat token so the old browser loses its claim. Names are unique per room, case and spacing ignored (a generated `name_key` column plus a unique constraint, so two simultaneous joins cannot both win). The same rules are in `decideJoin` (pure, tested) and in `join_room` (SQL); the shared contract suite runs against both.
- **Presence: Realtime presence plus a heartbeat.** The host watches presence and mirrors it into `players.connected` (a seat missing from presence is flipped only if its last heartbeat is over 10 s old, so a phone that just joined is not dropped before presence catches up). Phones also ping every 20 s into `player_secrets.last_seen`, which is deliberately not a `players` column so heartbeats do not fan out through Realtime. A seat counts as live only if `connected` and the heartbeat is under 60 s old, so a phone that died silently becomes reclaimable even if no host screen is open.
- **Client layer: a `Backend` interface with two implementations.** `app/src/net/` holds the game-facing code (join, resume, phone session, host session, room watcher with a pure `applyChange` reducer). The Supabase calls sit behind `Backend` (`supabaseBackend.ts`); `fakeBackend.ts` is an in-memory version with a controllable clock. One contract suite (`contract.ts`) runs on both, so the fake cannot drift from the database. The real-project run uses throwaway rooms and deletes them; it is skipped when the `VITE_*` variables are missing.
- **Housekeeping:** `create_room` deletes rooms untouched for 3 days (cascades to players, rounds and answers). `host_reset_played` clears play history except the current room's current game. `host_delete_room` also removes that room's history and blocklist rows.
- **Supabase free tier (checked 2026-11-26 against the docs):** a Free project is **paused after 1 week without enough database activity** (a warning email goes out about a week before; opening the dashboard or a few requests a day count as activity). Paused projects keep their data and can be restored from the dashboard (the docs say up to 1 year; a 2024 changelog said 90 days); only 2 active free projects per account. Before a party after a quiet spell, open the dashboard or run `node tools/apply-migrations.mjs --verify` to wake it, and do it a day ahead in case a restore takes a few minutes. Realtime on Free: 200 concurrent connections, 100 messages/s, 20 presence events/s, 2 million messages/month. One game (about 13 connections, a few dozen changes fanned out to each) is far below all of these; it would take hundreds of games a month to reach the message cap. Sources: https://supabase.com/docs/guides/platform/free-project-pausing and https://supabase.com/docs/guides/realtime/limits.
- **Game logic is pure TypeScript in `app/src/logic/`, with all tunables in one `CONFIG` object and randomness passed in.** No network or DOM imports, so rules, scoring, tie-breaks, the artist matcher and song selection are tested in isolation and can run on host or phone alike.
- **Artist matcher: typo tolerance by name length, strict about partial names.** Edits allowed grow with length (none up to 4 letters, 1 up to 10, 2 beyond). A strict subset of a name's words ("Lil Nas" for a three-word name) never counts. The surname rule applies to multi-word names unless the name starts with "The", contains "and", or is listed in an optional `groupArtists` song field; the song data has no solo/band flag, so this keeps the schema unchanged while letting the data phase mark bands.
- **Sudden death is one shared function for both modes.** Only tied players answer, the closest year wins, and a repeat tie (or nobody answering) plays another song.
- **Preview resolver is a standalone, resumable Node script (`tools/resolve-previews.mjs`).** One iTunes search per song, at least 3.2 s apart, with a 60 s back-off on HTTP 403/429. A result is accepted only if its title and artist match (remaster/feat suffixes ignored; live, karaoke, tribute and remix versions rejected). The earliest-released match wins, and `releaseDate` is used only for ordering, never as a song's year. Each clip URL is checked with HEAD or a 2-byte ranged GET, so no audio is downloaded. Progress goes to `data/work/previews.json` after every song. Offline test: `node --test tools/resolve-previews.test.mjs`.
- **UI: plain TypeScript and DOM, no framework; hash routing.** The host page is `#/host`, a phone is `#/join/ABCD` (what the QR code opens) or the bare page. The site is static files on GitHub Pages, which cannot rewrite paths, so the route lives after the `#`. A tiny `h()` element builder (`app/src/ui/dom.ts`) keeps screens as plain functions. The host lobby has only buttons, so it is rebuilt on every change; the phone join form is built once so typing is never interrupted. Reason: the lobby is a few screens, and a framework would be more code than it saves.
- **Lobby rules are pure and tested (`app/src/logic/lobby.ts`).** Settings from the room's loose JSON are clamped to ranges in `CONFIG.lobby`; the host can start with at least 2 connected players (`CONFIG.lobby.minPlayersToStart`); room codes typed on a phone are upper-cased and stripped of anything but letters.
- **Kicking a player is its own RPC (`host_kick_player`, migration `20261126210000`).** It checks the host token and deletes the player row (cascades to their answers), so the name is free again at once. The kicked phone sees its player vanish from the realtime feed and returns to the join form with a short message. On the host a kick needs two taps (the button turns into "Remove?" for 4 s), which also works on a touch screen with no `confirm()` dialog.
- **New dependencies:** `qrcode-generator` (small, no dependencies, draws the join QR as inline SVG) and `happy-dom` (dev only, lets the lobby component tests run in Vitest without a real browser).
- **Closest Year flow is a host-side controller with no state of its own (`app/src/game/closestYear.ts`).** Round progress (rounds played, sudden-death contenders, winner) is kept in the room's `settings`, and the current round is read back from the database, so a host refresh picks up where it was. Scoring, reveal building, overrides, "everyone answered" and the timer check are pure functions in `app/src/logic/closestYearRound.ts`; the controller only reads state, calls them and writes the result.
- **Phones only ever get the answer inside the reveal.** The song id stays host-only until `reveal()` writes the reveal JSON (title, artists, year, per-player rows), which is public from then on. Before that, a phone's readable state holds no song data (tested against both the public snapshot and `getMyState`).
- **Timer and early finish share one entry point (`checkAutoEnd`).** The host calls it on every lock-in and on a tick: it ends the round when every connected player (in sudden death, every contender) has locked in, or when `ends_at` has passed. Disconnected players never hold a round up. Writes run one at a time, so the timer and the last lock-in cannot reveal a round twice.
- **Host override re-scores from the public reveal, not from memory.** The reveal rows keep what each player typed, so `setArtistOverride` can re-score that one row, fix the player's score and artist-hit count, and re-check whether the game outcome changes, even after a host refresh. It re-publishes the reveal through the same RPC (the database allows re-reveal).
- **Sudden death does not score.** It runs only among the tied top players, one new song per round, closest year wins, and repeats on another tie. A skipped round (clip would not play) is not counted but its song stays in play history, so it never comes back.
- **Phone answers autosave while editing; Lock In is final.** The brief says answers can change until time is up, but the backend refuses a change after lock-in (`already-locked`, which keeps the "everyone answered" early finish honest). So the phone saves the year and artist as they change (debounced, `lock:false`) and Lock In ends editing. Nothing is lost if the phone drops out before locking in.
- **The year picker starts in the middle of the range, or at the player's last guess.** The start never depends on the song, so it gives nothing away. Pure helpers (bounds, step, press-and-hold timing, decade ticks and chips) live in `app/src/logic/yearPicker.ts`; the DOM part is `app/src/ui/yearPicker.ts`. Timings are in `CONFIG.yearPicker`.
- **Clips stream from Apple's URL on the host device only (`ClipPlayer` in `app/src/ui/hostGame.ts`).** An `Audio` element plays the preview URL, nothing is downloaded or re-hosted. Browsers block autoplay without a tap, so the host gets a "Tap to play" button, and if a clip fails to load there is a Skip song button. The player is injected so tests use a fake.
- **The host loads `songs.json` through an injectable `loadPool`.** By default it fetches `songs.json` next to the app (an array of songs, or `{songs: [...]}`). Tests pass a made-up pool.
- **Screens redraw only when the stage or round changes.** A phone's slider drag or typing is never interrupted by a state update. Phones refresh from their own state when the status, round, mode or their score changes, so a host override reaches them.
- **Timeline flow is a host-side controller on the same round loop as Closest Year (`app/src/game/timeline.ts`, pure rules in `app/src/logic/timelineRound.ts`).** `TimelineGame` has the same shape as the Closest Year controller (`begin`, `nextRound`, `checkAutoEnd`, `endRound`, `skipRound`, `setArtistOverride`, `playAgain`) and keeps progress in the room's `settings`, so a refreshed host resumes. A wrong or missing slot adds nothing and costs nothing; a correct slot adds the card. Artist hits are stored per player and count only for the tiebreak. Several finishers in one round go to most artist hits, then to sudden death (closest year, repeated) among only those still tied. Sudden death asks for a year, not a slot, and never changes a timeline or counts a hit.
- **Starter cards are dealt by the controller, and a late joiner gets a pair before the next song.** Each pair is two different years within the configured range and no two players share a pair where the range allows. Players with no cards are left out of the early-finish check and out of scoring, so they never hold a round up.
- **Phones see only their own timeline.** The `players` table is world-readable (an earlier decision), so this is enforced in what a phone reads and shows: `timelinePhoneView` is built from the phone's own state only. The song and everyone's answers stay host-only until the reveal. The integration test checks the public snapshot and each phone's state for the current song before the reveal.
- **Timeline screens are two modules per side, one per mode (`app/src/ui/phoneTimeline.ts`, `hostTimeline.ts`).** `host.ts` and `phone.ts` build both game modules and route on `room.mode`; each module draws only while the room is in its own mode and out of the lobby, and resets itself otherwise. Closest Year and Timeline therefore share no screen code and cannot disturb each other.
- **Slot logic is pure (`app/src/logic/slotPicker.ts`).** Labels ("Before X", "Between X and Y", "After X"), the correct slots for a year (equal years accept either side) and the select/keep rules are plain functions with tests. The DOM picker (`app/src/ui/timelinePicker.ts`) only draws them: a scrollable ordered row of year cards with a large tap target in every gap.
- **On the phone a slot is selected, autosaved, and freely changeable until Lock In (final) or time is up.** This matches the Closest Year rule and the backend's `already-locked`. Cards on the phone show years only, because the phone has no song data; after the reveal the card just won is highlighted by its song id.
- **The host shows card counts, never anyone's timeline.** The progress board shows cards out of the target for every player; the reveal lists who placed correctly and who hit the artist, with the override buttons. Timeline contents stay on the phones.
- **Blocklist and played history live in the database and need no new migration.** The existing block, unblock and reset calls already do the work. The blocklist is global and survives resets. "Reset played songs" clears only earlier games; songs already played in the current game stay out, so a song can never repeat inside one game. Because history is stored per room in the database, a second game on the same device group (Play again, or back to the lobby and start again) never repeats a song from the first. This is covered by `app/src/game/songHistory.test.ts`.
- **The restore list gets titles by loading the song list in the host's browser.** The database only stores song ids (so it holds no spoilers). `app/src/ui/hostSongs.ts` joins the blocked ids to the song list on the host screen only. An id that is no longer in the list is still shown (as "Song no longer in the list") so it can be restored.
- **Destructive or surprising host actions use a two-step confirm (`app/src/ui/songTools.ts`).** "Reset played songs" first explains that it makes every song available again, then asks to confirm or cancel. The same helper holds the "Remove from future games" control (with Undo) and the exhausted-pool notice.
- **A used-up pool says why, and offers a reset only when it would help.** `chooseNextSong` reports `resetWouldHelp`. If earlier games used the songs, the host sees a friendly message with the confirmed reset. If the songs are all used in this game or blocked, no reset is offered and the message points to the Song settings screen. Pure text and counts are in `app/src/logic/songLibrary.ts`.
- **Bot simulation runs the real net and game layers through vite-node, not a browser (`tools/simulate.mjs` + `tools/simulate-run.ts`).** It uses the same Supabase calls and the same host and phone controllers as the screens, against the real project with throwaway rooms that are deleted at the end (also on Ctrl-C). A killed "page" simulates a closed tab (no goodbye), and a graceful stop simulates moving to another device. The checks re-derive scores and placements from the answers the bots were told were saved, so they do not trust the app's own output. It prints counts and timings only; violations name round and bot numbers, never song fields.
- **A goodbye is not undone by stale presence (migration `20261126220000_goodbye_stays_away.sql`).** The simulation found that a phone saying goodbye was marked connected again within a second by the host's presence mirror, so a player moving to a new device got "name taken" for up to about 25 s. Now `seat_ping(false)` back-dates `last_seen`, and `host_set_connected` only marks a seat connected from presence if it was heard from in the last 10 minutes. A returning phone always sends a heartbeat or rejoins first, so real reconnects are unaffected.
- **Deploy: GitHub Actions to Pages, config in repository variables, tests gate the build.** The workflow runs `npm test` before `npm run build`, so a failing test stops a deploy. The Supabase URL and publishable key are repository *variables* (set by `tools/set-pages-vars.mjs`, never the database URL), because they end up in the public JavaScript anyway. `songs.json` is committed and served as a static file next to the app, as accepted earlier for a public repo; the song details stay out of every log and note.
- **Play Again starts clean (migration `20261127110000_new_game_clears_results.sql`).** Root cause: Play Again reset only scores and timelines, so the old game's last round (with its reveal, answers and locks) stayed the "latest round" and `room.settings` kept `winnerId`, so every screen that reads those showed the previous game's results until a new round replaced them. Fix: `host_new_game` (and the fake backend) delete the room's rounds, which cascades to answers, locks and secrets, and strip the result keys from settings; phones also drop a stale round when `game_no` goes up. Players keep their seats and names, and the played-songs history and blocklist carry over, so songs do not repeat.
- **Repeat years stack on a timeline.** Cards with the same year show as one pile with an x2 or x3 badge. Gaps go before and after a pile, never through it, and every card still counts toward the card target.
- **One top-5 leaderboard on the answer screen** (`leaderboardSize` in config), the same on host and phones, replacing the separate lists. Phones also show "You are Nth of M" for a player outside the top 5.
- **Up to 20 players (migration `20261127100000_max_players_20.sql`).** The limit lives in `CONFIG.maxPlayers` and the database check. The lobby uses two columns, and three on very wide screens. The free-tier Realtime numbers are in the section above.
- **No screen may stay frozen on an old game (resilience layer).** The first Play Again fix was correct on a healthy network (checked against the real project), but a page could still stick on the last game: a failed or lost state read left the screen as drawn and was never retried, a lost realtime event was never recovered, a hung request kept every button dead, a failed Play Again dropped the host back to the last reveal, and a tab left open for days ran old code. Now: `watchRoom` re-reads the room every `CONFIG.net.resyncSeconds`, when the tab returns and when the network returns, and applies it if different (a live change always beats a slower re-read); host and phone controllers retry a failed read after `retrySeconds`; button presses give up after `actionTimeoutSeconds`; `ackOver` resets only after Play Again worked; `ui/staleApp.ts` reloads a tab when the live page names a newer script (host and phone restore from storage). Tests: `net/watch.test.ts`, `ui/playAgain.e2e.test.ts` (both modes, muted realtime, failing reads, hung request, host and phone refresh), `ui/staleApp.test.ts`. `tools/playagain-live.ts` is a live check against the real project.
- **Decades are a room setting, not a pool edit.** The host picks decades on the Song settings screen; the choice is stored as `decades` (list of decade start years) in `room.settings`, which is shallow-merged JSON, so no migration. `chosenDecades()` treats a missing or empty list as every decade, and the last decade cannot be switched off. Song picking (`chooseNextSong`, both modes) filters by `decades` on every round, so it also applies to a game already in the lobby and survives host refresh and Play Again. Per-decade counts on that screen show fresh songs only. Pure helpers and tests: `logic/decades.ts`, `logic/decades.test.ts`; screen test in `ui/songHistory.e2e.test.ts`.


Opening the host page after a finished game: the host page resumes its saved room, and a room in `over` used to land straight on that game's winner screen (the "stuck on the last game" report). Now a resumed `over` room is reset with `host_new_game` first, so the host sees a fresh lobby with the same code and the players keep their seats. Reason: the winner screen is only useful in the moment, and a stale one looks like a freeze. Covered by a UI test in `playAgain.e2e.test.ts`.

A round ends with two separate writes: the reveal (with its outcome: continue, sudden death or winner), then the room (`status`, winner, sudden-death list). If the second never lands (dropped request, closed tab), the host used to sit on a reveal that said "winner" while the room was still `playing`, and "Final results" did nothing, so the page looked frozen and Play Again never appeared. Now `outcomeMismatch` (pure, in `game/closestYear.ts`) compares the reveal on screen with the room and `repairOutcome()` writes what the reveal already holds. It runs when the host page opens or syncs and when "Final results" is clicked. The phones' result screen also redraws when the game turns over (its redraw key had no "over" flag). Covered by three UI tests in `playAgain.e2e.test.ts` (backend that refuses the `over` write).

Lobby player list (2026-11-27): rows are an auto-fill grid (min 260px per cell) of avatar initial, one-line name with ellipsis and a title, and a kick button. The old two-column list with `word-break: break-word` let a flex name shrink to one letter per line next to the status text and button. Connection state is a dot on the avatar, plus a small "Reconnecting…" line under the name. `data-player`, `data-action=kick` hooks are unchanged.

Page structure (2026-11-27): three pages, chosen by hash (`ui/route.ts`). `#/` is the home page (`ui/home.ts`: what the game is, three steps, a Host and a Join button), `#/host` is the host page, `#/join` and `#/join/CODE` are the phone page (the QR code opens the second form). Unknown hashes land on home. Each page has a `← Home` link. Hash routing stays because the site is static files on GitHub Pages; the old bare address used to open the host page, and now opens home.

A finished game never comes back (2026-11-27): from the game-over screen, both "Play again" and "Back to lobby" end in `newGame()` (the `host_new_game` RPC: deletes the room's rounds, bumps `game_no`, zeroes scores and timelines, keeps players and settings). "Start" in the lobby also calls `newGame()` before `begin()`, so a host who changed settings after a game starts a clean game, never the old round and results. Before, "Back to lobby" only flipped the room status and Start reused the old round. Tests: `ui/playAgain.e2e.test.ts` (Back to lobby, change a setting, Start, in both modes).

Artist-guess panel (2026-11-27): the host reveal screens redraw wholesale on every room update (answers arriving, overrides, realtime), which rebuilt the `<details>` panel closed a moment after the host opened it. Its open state now lives in the host module (`checksOpen`, reset when the round id changes), and is re-applied on every redraw. Test: `ui/closestYear.e2e.test.ts`.

Hosting like Jackbox or Kahoot (2026-11-27): the host page remembers nothing. The host's credentials (room id and host token) used to sit in `localStorage` and were reopened on every visit, so a game hosted hours earlier came back instead of a new one. Now they live only in memory in the open tab: every visit to `#/host` starts a brand new room straight away (the Host a game button on the home page is the only step; there is no separate start page, and the lobby has a Home link like the join page), a refresh or closed tab ends that game for the host, and there is no list of past games. Many games at once need no extra code, since each tab or device creates its own room (the database already allowed many) and holds its own credentials. `clearOldHostStorage` deletes the keys earlier versions saved (`jukebox.host`, `jukebox.hosts`) so a leftover entry can never come back. Because a game now exists only in its tab, the new-version watcher does not reload a host tab with a game open (`hosting()` / `canReload`); phones restore their seat after a reload as before. `resumeSeat` takes the room code from a QR link and ignores a saved seat for a different room. Abandoned rooms clean up on the server after 3 days idle. Tests: `ui/lobby.test.ts` (fresh game on every visit, nothing saved, two games at once, legacy keys wiped), `net/contract.ts`.

- **Real-project tests are opt-in.** `real.test.ts` runs only with `RUN_REAL_TESTS=1`, uses throwaway rooms and `test-*` song ids, and skips tests that touch shared tables (`host_reset_played` clears every other room's played history). `watchRoom` re-reads once shortly after subscribing (`CONFIG.net.firstResyncSeconds`) because Realtime can report SUBSCRIBED just before changes flow.

- **Round no longer ends early in small groups (2026-11-28).** A phone that sleeps or is backgrounded loses its presence and its 20s heartbeat; after about 10s the host marks it away (`connected=false`), and "everyone has locked in" used to ignore away players, so with 3-4 players the others locking could end the round while that player was still thinking. Each game class now keeps a roster of who was connected when the round opened (`roster`, `waitingFor`) and keeps waiting for them until the timer ends the round. A player who joins mid-round is not waited for. The 10s away threshold on the server is unchanged. Tests: `game/closestYear.test.ts`, `game/timeline.test.ts`.
- **Start game goes straight to the game (2026-11-28).** Timeline used to set the room to "playing" and only then deal the two starting cards, so phones drew the game with an empty timeline and redrew a moment later. `begin()` now deals first, then flips the room to "playing". Test: `ui/startFlash.e2e.test.ts` (records every screen each device shows, with simulated network lag).

After a song, the phone result screen shows the right answer (`ui/answerBlock.ts`), and the host's artist-check panel also lists each player's year guess (no override for years).
